# v1.2.0 — 同步目标改为「发布标签驱动」

- 类型：功能变更（新增能力 + **默认值变更**）
- 日期：2026-09-19
- 关联：CR-005（本版主体）
- 状态：代码与文档已落地；**引擎 commit 与发布标签均尚未 push origin**（见「已知限制」）

## 背景

v1.1.0 交付了本机多宿主同步器，但它的默认目标写成了「本机引擎仓 HEAD」。这意味着
**引擎每提交一次，本机所有宿主就该重新 pin 一次**——而「提交」与「值得让宿主移动」并不是一回事。

实测数据：`6fadcb2`、`c6c32b4` 两个**纯文档 / 记忆**提交各触发一轮 3 宿主 gitlink 更新；
上一轮收尾时甚至为避免这个副作用而**故意不提交**记忆文件（导致工作区长期留着一处未提交改动）。
这与 §8.4 的项目约定直接冲突——该约定明确「只有影响宿主调用行为（参数 / 默认值 / 输出 JSON 字段 /
退出码 / 生成物路径）的变更才升版本」，其**存在意义就是让宿主不必跟着文档变动走**。

本版把同步目标与**发布标签**绑定：标签只在判定为行为变更时才推进，于是「升版本」从纯文档动作
变成了**宿主移动的唯一触发器**。

## 内容

1. **同步目标三值化**：`--target release | local | origin`（默认 `release`）
   - `release`：最新发布标签 `v*`（`--sort=-v:refname` 语义版本排序），日常使用
   - `local`：本机 HEAD，引擎开发期联调
   - `origin`：`origin/HEAD` 指向的分支，交接 / 多机 / CI（`--from-origin` 保留为别名）
   - **无标签时不静默退回 HEAD**：直接报错并给出「先 `--tag`，或临时 `--target local/origin`」的指引
2. **发布标签动作 `--tag vX.Y.Z`**：在当前 HEAD 打注解标签。内置护栏（任一不满足即拒绝）：
   - 标签格式须为 `vX.Y.Z`
   - **引擎仓工作区必须干净**（发布标签必须指向可复现的提交）
   - 标签不得已存在（发布标签不可移动）
   - **必须与 `STATUS.md` 的 `project_version` 一致**——把「升版本」从人的自觉变成机械约束
3. **发布 + 同步一条命令**：`--tag vX.Y.Z --apply` 先打标签，再以该新标签为目标同步各宿主（推荐主路径）。
4. **新增状态 `ahead-of-target`**（宿主 pin 是目标的**后代**），并定义为**良性**：
   不计入「需人工处理」、`--check` 不因此返回 `2`；默认不动，回落需显式 `--allow-downgrade`。
   状态判定同时修正为「`pinned == target` → `up-to-date`」，不再用 `behind == 0` 反推。
5. **钩子语义随新默认修正**：`--install-hook --auto` 从「每次提交后 apply」改为
   **「仅当 HEAD 正好落在发布标签上时才 apply」**，定位为兜底；「仅提示」模式也修好了
   （原先 `--check --quiet` 会把要打印的报告一起吞掉，与注释不符）。
6. **输出 JSON 扩展**：`engine` 增 `target_short` / `release_tag`（无则 `null`）；
   新增 `summary{total, outdated, ahead_of_target, attention}`。
7. **一次性迁移**：补打 `v1.1.0` 标签（指向 `0734932`），作为发布标签约定的起点；
   `v1.0.0` 按 §1 语义（治理基线快照、非发布版本）**不打标签**。版本号 ↔ 发布标签的绑定写入 §1 与 §8.4。

## 效果

- **纯文档 / 记忆提交不再惊动任何宿主**：`--check` 显示全部 `up-to-date`，零 gitlink 更新。
- 「宿主该跟到哪个版本」从隐式约定变成**可回答的问题**：答案就是最新发布标签，且可从宿主仓库的
  gitlink 反查出对应版本（`git describe --tags <gitlink>`）。
- 发布动作自带版本一致性护栏，`STATUS.md` 忘改版本号时**打标签会失败**，而不是留下一个语义错位的标签。
- 回滚路径明确：宿主 pin 比发布版本新时默认不动，不会把已含新行为的宿主「降级」回旧标签。

## 兼容性

**默认值变更**：不带 `--target` 直接运行 `--check` / `--apply` 时，语义从「跟本机 HEAD」变为
「跟最新发布标签」，且在引擎仓**无 `v*` 标签时报错退出（code 1）**而非静默继续。

参数层面**向后兼容**：`--from-origin` 仍是有效别名；其余参数、退出码语义不变。
`archive_upload.sh` / `pgy_upload.sh` / `link-skill.sh` **零改动**，宿主调用链不受影响
（`sync-hosts.sh` 只在本机跑，不进入宿主工程）。

## 已知限制

| 项 | 说明 |
| --- | --- |
| **引擎 commit 与发布标签均未 push**（`OPEN-005`） | 本机 HEAD 与 `v1.2.0` 标签都还没推。标签不 push，他人 / 新克隆就看不到 release 同步目标；宿主 pin 的 commit 也解析不到。push 由使用者主导（本机 sandbox 无 codeup 凭证）。 |
| 「无标签」是硬失败 | 这是刻意设计（避免静默退回 HEAD），但意味着**新克隆的引擎仓在拿到标签前，`--check` 会直接报错**。首次交接时需先 `git fetch --tags`。 |
| 钩子赶不上常规发布顺序 | 常规顺序是「先提交、后打标签」，而 `post-commit` 对 tag 不生效——所以钩子(`--auto`)只覆盖「提交时 HEAD 已带标签」的非常规路径，**发布主路径必须显式跑 `--tag … --apply`**。已在 §3.3 与钩子注释中写明。 |
| `--tag` 只对当前 HEAD 生效 | 因此**补打历史版本标签必须用原生 `git tag -a <tag> <commit>`**（且会绕过 `project_version` 护栏），如本版的 `v1.1.0`。属一次性迁移动作，未做成工具能力。 |
| `OPEN-001` / `OPEN-002` 仍在 | Xcode 不热加载外部手改的共享 `.xcscheme`；`--notes` 仅在 CLI 入口生效。均属 by-design，靠文档与 CLI 入口规避。 |
