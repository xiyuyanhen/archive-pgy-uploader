## 评估：submodule 共享 vs 软链共享（只评估，未落地变更）

**结论**：两者不在同一层——软链适合「暴露/发现」，submodule 适合「依赖锁定」。现有分层（submodule 存引擎 + `link-skill.sh` 软链注册技能 + 独立 `archive-pgy-config/`）是正确的，不建议把引擎共享改为软链。

**软链的硬伤（按严重度）**
1. 无版本锚点 + 单一工作区 → 不可能并行版本；「今天行为变了」无法从宿主仓库追溯。
2. 跨仓库软链在 git 中只能是符号链接对象：commit 之 → 新克隆/队友/CI 必断链；gitignore 之 → 宿主对依赖的存在与版本**零记录**。
3. `rm -rf <link>/`（带尾斜杠）会**穿透**删除中央实体内容（AI 批量清理场景真实存在）。
4. 通过软链路径编辑 = 直接写进中央仓库当前分支，宿主 `git status` 无感知 → 误提交方向错误。
5. 沙箱/IDE/CI 对工作区外路径的访问限制；XcodeGen 可能沿软链枚举文件（需实测）。

**软链的真实优势**：零更新摩擦（pull 一次全宿主生效）、磁盘 0 复制、单一工作区便于调试、不引入子模块状态机。适用于「单人 + 单机 + 引擎频繁迭代 + 不需并行版本」。

**实测证据（三宿主三种接法，本身即最有力论据）**

| 宿主 | 接入方式 | 版本锚点 | 实测 |
| --- | --- | --- | --- |
| xiyuScoreboard | submodule | gitlink `6576a6f` | 落后引擎 HEAD **4 个 commit**（缺 STATUS/changelog/experience） |
| xiyu_todo_list | submodule | gitlink `155046c` | 落后 2 个 commit；`ios/Scripts/archive_upload.sh` 为薄包装转发（设计正确） |
| xiyuWebBrowser | **目录复制**（宿主按普通 blob 跟踪，非 gitlink；内含独立 .git） | **无** | `skill/SKILL.md` 与引擎不一致；缺 STATUS/changelog/experience；遗留 33KB `PGYUploadScript.sh`；`pgy_config.sh`(密钥已填实 len=32) + `PGYUploadHistory.json` 混在引擎目录内（好在被副本 `.gitignore` 忽略，未入库） |

→ 问题不是「submodule 还是软链」，而是**没有单一机制时人力会退化为复制**。

**建议（待用户确认后再按 §8 走 CR）**
1. 引擎共享层保持 submodule；软链限定在暴露层（`link-skill.sh` 已是此定位，勿扩大）。
2. 收敛 xiyuWebBrowser 为 submodule；至少先把 config/history 移出引擎目录。
3. 嫌 submodule 更新摩擦 → 补更新命令（`git submodule update --remote` + commit gitlink），**不要**换软链。
4. 可选 dev mode：本地软链覆盖仅用于引擎开发，必须 gitignore + 标注「无版本锚点、勿用于交接/CI」。

**连带风险**：软链模型下引擎只有一份实体，项目差异只能靠 `--config` 区分；一旦有人把 config 放进引擎目录，所有宿主共用同一份 `TARGET_BUNDLE_ID`，C3 的 Bundle ID 校验会立刻失效。
