## 评估：submodule 共享 vs 软链共享（只评估，未落地变更）

**结论**：两者不在同一层——软链适合「暴露/发现」，submodule 适合「依赖锁定」。现有分层（submodule 存引擎 + `link-skill.sh` 软链注册技能 + 独立 `archive-pgy-config/`）是正确的，不建议把引擎共享改为软链。

**软链的硬伤（按严重度）**
1. 无版本锚点 + 单一工作区 → 不可能并行版本；「今天行为变了」无法从宿主仓库追溯。
2. 跨仓库软链在 git 中只能是符号链接对象：commit 之 → 新克隆/队友/CI 必断链；gitignore 之 → 宿主对依赖的存在与版本**零记录**。
3. `rm -rf <link>/`（带尾斜杠）会**穿透**删除中央实体内容（AI 批量清理场景真实存在）。
4. 通过软链路径编辑 = 直接写进中央仓库当前分支，宿主 `git status` 无感知 → 误提交方向错误。
5. 沙箱/IDE/CI 对工作区外路径的访问限制；XcodeGen 可能沿软链枚举文件（需实测）。

**软链的真实优势**：零更新摩擦（pull 一次全宿主生效）、磁盘 0 复制、单一工作区便于调试、不引入子模块状态机。适用于「单人 + 单机 + 引擎频繁迭代 + 不需并行版本」。

**实测证据（三宿主三种接法，本身即最有力论据）**

| 宿主 | 接入方式 | 版本锚点 | 实测 |
| --- | --- | --- | --- |
| xiyuScoreboard | submodule | gitlink `6576a6f` | 落后引擎 HEAD **4 个 commit**（缺 STATUS/changelog/experience） |
| xiyu_todo_list | submodule | gitlink `155046c` | 落后 2 个 commit；`ios/Scripts/archive_upload.sh` 为薄包装转发（设计正确） |
| xiyuWebBrowser | **目录复制**（宿主按普通 blob 跟踪，非 gitlink；内含独立 .git） | **无** | `skill/SKILL.md` 与引擎不一致；缺 STATUS/changelog/experience；遗留 33KB `PGYUploadScript.sh`；`pgy_config.sh`(密钥已填实 len=32) + `PGYUploadHistory.json` 混在引擎目录内（好在被副本 `.gitignore` 忽略，未入库） |

→ 问题不是「submodule 还是软链」，而是**没有单一机制时人力会退化为复制**。

**建议（待用户确认后再按 §8 走 CR）**
1. 引擎共享层保持 submodule；软链限定在暴露层（`link-skill.sh` 已是此定位，勿扩大）。
2. 收敛 xiyuWebBrowser 为 submodule；至少先把 config/history 移出引擎目录。
3. 嫌 submodule 更新摩擦 → 补更新命令（`git submodule update --remote` + commit gitlink），**不要**换软链。
4. 可选 dev mode：本地软链覆盖仅用于引擎开发，必须 gitignore + 标注「无版本锚点、勿用于交接/CI」。

**连带风险**：软链模型下引擎只有一份实体，项目差异只能靠 `--config` 区分；一旦有人把 config 放进引擎目录，所有宿主共用同一份 `TARGET_BUNDLE_ID`，C3 的 Bundle ID 校验会立刻失效。

## 23:1x 同步目标改为「发布标签驱动」（v1.2.0 / CR-005）

用户拍板：把同步目标从「每个 HEAD」改成 tag（只有行为变更才移动）。落地要点：

- **`--target release | local | origin`**（默认 `release` = 最新 `v*` 标签，`--sort=-v:refname`）。
  **无标签时直接报错并给指引**，不静默退回 HEAD。`--from-origin` 保留为 `--target origin` 别名。
- **`--tag vX.Y.Z`**：打发布标签。护栏 = 格式合法 + 工作区干净 + 标签不存在 + **与 `STATUS.md` `project_version` 一致**。
  补打历史标签必须用原生 `git tag -a <tag> <commit>`（`--tag` 只对 HEAD 生效且会被版本护栏挡住）。
- **`--tag vX.Y.Z --apply` = 发布 + 同步（主路径）**。原因见下。
- **新增状态 `ahead-of-target`**（宿主 pin 是目标的**后代**）= 良性：不计入 attention、`--check` 不返回 2、默认不动，
  回落需 `--allow-downgrade`。`up-to-date` 改为 `pinned == target` 直接判定（不再用 `behind == 0` 反推）。
- **JSON 扩展**：`engine.target_short` / `engine.release_tag`（无则 null）+ `summary{total,outdated,ahead_of_target,attention}`。

### 关键设计判断（勿反复推翻）
- **标签即「值得让宿主移动」的判据**：把 §8.4「影响宿主调用行为才升版本」从文档约定变成机械触发器。
  升版本 → 打标签 → 宿主移动，三者绑定。**不该升版本时不要打标签**。
- **`v1.0.0` 不打标签**：按 §1 语义它是治理基线快照、非发布版本（CHANGELOG 早已如此声明）。
  `v1.1.0` 事后补打（指向 `0734932`），作为发布标签约定的起点。
- **钩子只能当兜底**：git 没有 `post-tag`，常规顺序「先 commit 后 tag」下 `post-commit` 永不触发 →
  `--auto` 改为「仅 HEAD 正好是发布标签时才 apply」。发布主路径必须显式 `--tag --apply`。
- **`ahead-of-target` 必须判定为良性**：否则开发期（宿主跟过本机 HEAD）会让 `--check` 一直返回 2、钩子一直报警。

### 本轮踩到的坑（已沉淀）
- **L-009**：`set -o pipefail` 下 `jq … | grep -q` 会让条件**反向判假**（读端提前退出 → 写端 SIGPIPE 141 →
  管道判非零 → 重复登记检查反而放行）。3 条数据量下不触发（输出远小于管道缓冲），属**潜在**缺陷。
  修法：`jq -e 'any(...)'` 内联判定；取首行用 `${t%%$'\n'*}` 而非 `| head -1`。
- **L-010**：git 无 `post-tag`；`git tag` 不产生 commit，`post-commit` 不会因打标签触发。
- 钩子「仅提示」模式原写 `--check --quiet` → `--quiet` 把要打印的报告一起吞掉（与注释不符）；
  改为静默取退出码、仅 `rc=2` 时重跑打印。

## v1.3.0 — 「半套接入」（unregistered-gitlink）检测与自动补登

### 做了什么
- `sync-hosts.sh` 新增状态 `unregistered-gitlink`：`.gitmodules` 已入库 + 目录是合法子模块 checkout，
  但 gitlink 未登记（`git submodule status` 为空）。`--apply` 自动补登（`git add -- <子模块路径>` + 本地 commit），
  落后于目标时先 `fetch` + `checkout --detach <目标>` 再补登（补登 + 对齐一条命令）。
- 新增 `is_submodule_checkout()` 安全边界：**只**对 git dir 落在宿主 `.git/modules/` 下的真子模块 checkout 补登；
  vendored 副本 / 嵌套仓库仍报 `not-a-submodule` 并提示走 `git submodule add`。
- JSON 新增 `summary.unregistered` 与 `status: "unregistered"`；`--check` 退出码把 `UNREG>0` 也计入 `2`。
- 同批修掉一个**既有缺陷**：rows.tsv 中 `pinned` 为空 → 连续 tab → bash `read` 折叠（tab 属 IFS 空白字符）
  → apply 循环整行左移（`state` 变 `N`、ACTION 变 `skip:<dirty值>`，还写进 JSON）。修法：所有列写非空占位符 `-`。

### 关键订正（勿再用旧说法）
- `unregistered-gitlink` 的危害**不是**「`update --init` 报错」，而是**静默**：新克隆后
  `.gitmodules` 有声明但 git 不认识该路径 → `git submodule status` 空、子模块目录**不存在**、
  `git submodule update --init` **退出码 0（不报错也不检出）**。CI/新同事 clone 后一切「成功」，
  直到构建时才发现引擎脚本缺失 → 排查方向极易跑到「构建配置」而非「登记不完整」。
- 判断子模块接入是否完整，**看索引模式是否 `160000`**，不要看磁盘目录/文件是否存在（都可能是假象）。

### 新沉淀
- **L-012**：`IFS=$'\t'` 下 bash `read` **折叠连续 tab**（非空白分隔符如 `:` 才保留空字段）；
  `jq split("\t")` 与 `awk -F'\t'` 都**保留**空字段 → 同一份数据两套解析器结果不同。
  修法：把「所有列非空」作为**写入侧**不变量。
- **L-013**：`.gitmodules` 入库但 gitlink 未登记的成因（单独 commit `.gitmodules`，或 `git rm --cached` 后没重 `git add`）、
  静默危害、识别方式、与 vendored 副本的区分、补登做法。

### 刻意不做
- `uncommitted-gitlink`（人已 `git add`、只差 commit）**不自动提交**——可能是人工编辑中间态。
- 夹具必须含**反向对照**（host-c vendored 副本不得被登记）：只证明「该修的能修」不足以证明安全。

## CR-009 — 远端可核实性的实测边界（公开 vs 私有）+ 本机全局 URL 重写（无版本变更）

**触发**：使用者问「把本仓远端换成 GitHub 后，你能否查到标签状态？」——CR-008 的 L-014 写成
「沙箱无法核实**任何**远端状态」，属**过度概括**，本轮实测收窄。

### 实测结果
- **公开远端可匿名查询**：`git ls-remote https://github.com/git/git 'refs/tags/v2.43.0'`
  → `rc=0` + 真实 tag SHA；`GIT_CONFIG_GLOBAL=/dev/null`（绕过全局重写）结果一致。
- **「确实没有该标签」的活样例**：查 `refs/tags/v9.9.9-does-not-exist` → `rc=0` 且 stdout/stderr 皆空。
- **私有远端**：codeup `info/refs?service=git-upload-pack` 直接 curl → **HTTP 401**
  （= 网络通、纯粹缺凭证；不是「不可达」）→ git 索要用户名 → rc=128。
- **沙箱无 GitHub 凭证通道**：`gh` 未装、`GITHUB_TOKEN`/`GH_TOKEN`/`GIT_TOKEN`/`GITHUB_PAT` 未设置、
  `~/.config/gh/hosts.yml` 不存在。
- **本机全局 `url.*.insteadOf` 同时改写 fetch 与 push**（仅 `insteadOf`、无独立 `pushInsteadOf`）：
  `https://github.com/foo/bar.git` 的 `get-url` 与 `get-url --push` **都**变成 `https://ghfast.top/...`。
  → **安全含义：把远端指向 GitHub 后，推送凭证会经第三方加速镜像。**
  → 判读远端地址必须用 `git remote get-url --push <remote>`，不能只看 `git remote -v` 字面值。
- 另有全局规则 `url.file:///tmp/SDWebImage.insteadof https://github.com/SDWebImage/SDWebImage.git`，
  而 `/tmp/SDWebImage` **不存在** → 该库拉取异常时报错与「远端不可达」无关，先查此规则（留档）。

### 结论（回答使用者的问题）
**公开 GitHub 仓：能查标签状态；私有仓：不能**（401 → rc 128，沙箱无凭证）。
⚠️ 但换远端前必须先处理全局 `insteadOf` 重写（凭证流向），且换完要 `git fetch` ——
否则 `origin/master` 是旧远端的陈旧值，`--target origin` 会给出**过期目标**（`sync-hosts.sh:422-423`）。
